## Separate provenance, not fabricated confirmation

A public HistoryReceiptWire still carries no confirmation/current flag. The
history client now offers a separate opaque runtime delivery object constructed
ONLY after its own successful one-shot authenticated transport. Consumption is
bound to the SAME live originating client and exact object pointer, once; client
copies share consumption, object copies/zero/unrelated objects fail. Close or
request failure yields no usable delivery. No parser or caller boolean creates
one. The original DATA method does not return delivery provenance.

Journal's new `RecoverHistoryOwned` uses that actual owned transport and consumes
its delivery itself, then follows all existing exact-device/current-policy,
finite persisted-attempt, cancellation, elapsed/wall time, durable pin and
immutable-anchor checks. Only after successful pin and final checks, and within
the ORIGINAL receipt access interval and intent deadline, can it retain private
SAME-runtime `historyReady`. This is NOT `finalizationReady`, proof engine
confirmation, renewed source eligibility or evidence of a live upstream account.
Original source/challenge expiry does not renew and does not block a historical
identity comparison; current policy and original access expiry still govern the
local sink. The actual source-of-truth current credential endpoint independently
rejects deletion/revocation/expiry. An immutable receipt cannot certify those
current facts, and there is no immediate upstream-revocation promise.

The private daemon owner supplies no receipt/challenge/secret/key argument. It
owns the original State byte revision/key and installed policy before disclosure,
rechecks them before and after I/O, and retains its owning Journal only on
successful fresh delivery. Its preparation is explicitly historical and has NO
confirmed proof receipt. Finalization dispatch is only routing; Journal's private
runtime readiness, exact image and pin enforce the authority boundary. DATA-only
history and file/reopen cannot acquire this readiness. Close/fault/stale context
prevent its use.

## Strict record7 and sole-State protocol

New record7 retains the entire strict record6 history and its exact immutable
first receipt, plus original State revision, exact installed policy byte revision,
original receipt digest and random fixed finalization ID. Its only phases are
native-finalization-prepared/completed. Validation reconstructs and strictly
validates the original record6 and its original record4. Receipt projection is
read from history; no WorkflowReceiptWire or ConfirmationMAC is fabricated.
Old record grammars reject its fields. Native State's credential grammar is
unchanged and correlation admits record7 only for its exact document/revisions.

`FinalizeHistory` accepts no receipt or confirmation parameter. It requires
private runtime readiness for this exact Journal image, policy, live original
access interval and exact on-disk canonical pending bytes. It durably publishes
the prepared marker BEFORE exposing the unchanged original secret to the narrow
native callback. The callback reuses actual sole-State saveChecked with native
owner lock, original identity/policy byte revisions and pre/post-publication
cancellation/wall/elapsed/expiry checks. Only that State can be usable. Completion
then correlates the SAME document. Existing exact native State can finish
historical completion after owning reopen, without rewriting State or network I/O.

Rollback-safe local publication can retry only in the same runtime and must
preserve exact finalization ID and original revisions. Ambiguous publication
freezes, and owning reopen discovers whole images. A prepared marker plus old
legacy State still blocks NORMAL New/LoadState. Missing State never creates a
replacement key. Pending-only record5 and record7 restart recovery are deliberately
not bypassed in this delta. Lost runtime readiness requires separately engineered
explicit authenticated recovery, not a setter or normal loader relaxation.

## Evidence and remaining limits

Forty-seven focused Journal scenarios cover four persistence boundaries
(lookup marker, lookup receipt pin, finalization prepare, finalization complete),
all eight faults plus success each; DATA-only, expired access, policy after pin,
cancel/Close in flight, replaced pending bytes, policy at finalization, callback
failure/retry identity and Close/fault readiness. Reopen cannot manufacture
readiness and only an existing exact State can correlate. Actual native durable
key/source tests add fourteen recovered-history sole-State cases: success, all
eight publication faults, policy before/during/after and expiry during/after.
They inspect unchanged or whole published State, safe retry fixed identity,
normal loader conflict, key retention, snapshot secret omission, legacy startup
refusal and current-client checks. Transport object zero/copy/client/Close/replay
probes complement existing verified TLS/purpose/origin/redirect/loss tests.

Independent review is required before acceptance. No installed/physical outcome
is claimed. The accepted immutability fix is forward-only: earlier buggy images
that erased their first pin cannot recover that lost anchor retrospectively.

process budgets. Production provisioning, lease/renewal/account-event revocation,
old executable controls, D1 runtime and OS/direct WireGuard/desktop/input are
