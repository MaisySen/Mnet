## Actual ownership boundary

The new private daemon `proveNativeEnrollment` accepts only context and explicit finite native limits. It cannot accept a caller challenge, expected identity, key, secret or receipt. It retains the original actual native preparation/State owner/policy revision, then asks the SAME actual Journal to begin the verified-origin workflow-v1. Normal TLS and independent own-PKCE checks remain in that channel, not replaced by public challenge/receipt equality.

Before a key callback can run, actual Journal durably saves `workflow-key-use-may-have-started` in the SAME record4 with the already-pinned full challenge, reserve ID, original intent, limits and credential. No response MAC exists yet. Failure before rename invokes no callback; possible publication freezes/no callback. A successful marker remains spent even when the callback declines. Reopen does not reconstruct admission or automatically repeat key use. Existing record4 shapes remain byte-compatible; an older strict decoder rejects the unfamiliar key-use phase rather than treating it as challenge DATA. This is not old-executable or downgrade-floor acceptance.

Only then can the Journal offer a runtime-only `WorkflowKeyAdmission`. Its unexported shared owner binds exact live Journal, exact in-memory image pointer, live original channel and operation cancellation. Copies share one spent flag. It cannot be built from DATA or reopened files. After marker publication Journal rechecks policy/principal/time outside its lock before offering the callback. A retained admission is invalidated on callback return, Close, phase change, cancellation, uncertainty or original deadline. `Respond` rechecks under the Journal lock, reconstructs full expected identity from original own-PKCE/service/reserve and only admitted bounded registrar times, then invokes finite local computation at most once. It has no private-key getter or State writer. This API is internal composition, not a new remote permission.

The actual private daemon callback first holds `d.mu` and rechecks retained owner/key/policy/State bytes plus unchanged original preparation. It refuses any existing legacy credential, AuthKey, exit-node or subnet/exit-use capability before begin and again before key use. It then consumes the admission while still holding `d.mu`, so the lock order is native then Journal. Close takes that same order. Journal never runs its policy/current callback or remote I/O under its lock. Native key bytes are decoded only inside the admitted local computation, not in advance from untrusted Challenge DATA. Actual proof engine compares the full independently reconstructed binding before X25519. Temporary mutable arrays are cleared, but Go strings/copies are not claimed zeroized. Filesystem ownership checks are not isolation against an adversarial same-UID writer.

After local proof the actual Journal checks current context again, saves the existing submit-may-have-started marker with response digest, performs the SAME one-shot submit and durably pins exact authenticated receipt DATA. The daemon verifies the returned confirmation against its own outstanding proof and checks current owner/policy again before returning receipt DATA. A wrong confirmation can leave historical receipt DATA pinned, but never yields accepted native output, installs State or authorizes a tunnel. Lost submit may have committed remotely and stays unknown. No refund/retry, new reserve or rotated key/secret is inferred.
