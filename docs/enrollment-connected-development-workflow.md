# Connected private development registrar workflow

This batch composes real configured Multies source transport, owned v4 proof and one actual Store node/claim/consumed-proof/receipt publication. It is no longer a test-only prepopulated receipt. It is still PRIVATE, unregistered and off unless explicitly invoked by internal code with separately installed private development files. No production startup caller, native daemon key caller, registrar HTTP begin endpoint, native State publication, deployment or screen/input permission is added.

## Where authority comes from

Multies remains the consent/current-eligibility source. Actual reserve-evidence-v2 authenticates the configured registrar service and original ticket/launch/mapping, checks the original approved person/session/workspace, exact current service and operator mapping, correlated live eligibility, immutable reserve descriptor and deadline. It emits checkedAt and namespaced principal/per-handoff session binding, but authorityGranted:false and NO network access-until. Historical status/ack and old List capability cannot substitute for this evidence.

Registrar is the trusted network authority in the agreed architecture. This workflow reads a NEW explicit private `StatePath.registrar-workflow-v1.json` only when its private begin/submit methods are explicitly called. All fields are required, unknown/duplicate/case aliases/fractional numbers refuse. Version must be 1 and mode literally development. Independently loaded existing `StatePath.registrar-sources-v1.json` resolves the configured source alias/service/bearer and allowed mappings. The nested LocalConfigV2 supplies exact principal authority/namespace, source origin, issuer label, registrar origin, audience, service and named principal/workspace/network bindings. Missing/mismatched config denies; a changed/removed file retires this owner permanently. Restoring bytes does not revive its old ephemeral challenges. Close/freeze also closes all proof owners and source work.

Explicit fields, no defaults: revision, source_id, policy, challenge_ms, max_lease_ms, max_observation_age_ms, clock_uncertainty_ms, max_live, max_live_per_principal, max_proof_attempts, max_attempts, max_records, max_state_bytes. Numeric validation ceilings are engineering bounds, not production capacities or a user-approved duration. The fixture explicitly chooses 10s challenge, 15s maximum lease, 20s observation age, 1ms uncertainty, four live/per-principal/proof attempts, eight attempts/records and 1MiB state. Effective INITIAL usable lease is the MINIMUM of configured lease, proof freshness, observation freshness and SAME source reservation deadline. In that fixture it is at most 10s. There is NO renewal and no claim this is useful production session duration.

This is a registrar-issued bounded development lease based on authenticated observed consent, NOT a source-issued network grant. The trusted source checkedAt is still subject to explicit cross-host clock assumptions. Future source revocation can occur after observation; existing current credential checks enforce the stored access deadline and explicit Store revocation, not continuous Multies eligibility. No production duration, logout/account-event effect, immediate revocation guarantee or real service configuration is selected.

## One owning connected path

1. `beginRegistrarEnrollment` accepts original private ticket/launch/mapping plus the presaved secret, never caller Binding/evidence/clock/proof=true. Canonical nonzero secret TEXT SHA256 must match original launch digest BEFORE source I/O. Descriptor syntax, exact current local mapping, actual existing network, permanent claims/scoped attempt-reserve-handoff conflicts and Store health are checked first. Existing unclaimed legacy nodes with the same raw key cannot be silently migrated.
2. Reserve bounded live/global/attempt/record/serialized-byte capacity before remote source, DH, IDs or IP allocation. A 256KiB whole-entry envelope is conservatively reserved per outstanding admission, with strict 16KiB source body bounds and a later exact serialized candidate cap. Exact output bytes are checked again before publication. No history or live attempt is evicted to create authority. Per-principal live slots are checked against authenticated observed identity before DH. Proof checks have a finite no-refund per-challenge budget. Source pool has its own independent finite/concurrency bounds.
3. Source request happens OUTSIDE Store mutex through actual Store-owned configured source pool, verified HTTPS and existing strict response decoder. Lost/invalid response spends this process's attempt, returns no challenge and cannot be retried by changing metadata under the same attempt. Exact already-admitted live begin retry returns SAME original challenge/deadline without source request or renewed lease. The source row itself keeps a sticky immutable reserve across Store restart.
4. Recheck actual current source and workflow fingerprints after I/O, exact source-row principal/service/mapping, source clock age and remaining bounds. Generate server-owned ID/nonce/ephemeral private key through reviewed proof engine only after successful admission. Bounded generation rejects own/live/retained ID and nonce cross-collisions. No ticket/raw bootstrap secret is retained in ephemeral attempt state or persisted in Store; only a hash of the original private request is retained for exact retry.
5. `submitRegistrarEnrollment` selects the original server-owned attempt, checks exact echoed challenge ID and same presaved secret, current config/time/health and finite proof budget. Response is ONLY raw MAC, never a replacement Binding/server key/expiry/permit. Owned proof verification is side-effect-free until Store commit. Invalid/wrong-ID/secret/MAC cannot allocate a node or consume a durable proof. Rollback-safe publication retry uses SAME owned proof, within remaining budget/deadline, not Join+Approve.
6. Under SAME Store mutex, recheck strict existing history and conflicts. Generate checked CSPRNG node/receipt IDs, allocate one mesh IP, make one approved node with no account identity, legacy NodeToken/AuthKey, routes or exit. Prepare one candidate with permanent raw-key claim, full owned challenge/transcript digest, v2 consumed-proof index, qualified immutable receipt and digest credential. Legacy v1 records remain unchanged if namespace promotes explicitly to v2; no old record is given invented consumption history. One guarded Store publication persists the entire candidate. Rollback-safe failure restores all maps/cursor/namespace. Ambiguous or late postpublication error freezes, returns NO receipt/confirmation and does not notify maps.
7. Guard immediately before rename and after sync rechecks current file fingerprints, health, caller cancellation, backward wall clock, monotonic elapsed and all finite timing bounds. No network is held under Store lock. Only after durable guarded success: mark ephemeral owner committed, close proof key, publish one map change and return historical receipt plus separately derived confirmation. Exact submit retry returns original receipt/confirmation only for SAME secret/response, without new time/ID/IP/save/version change. It is history, not a renewed current-enrollment flag.
8. Owning reopen resolves one whole persisted image. Private existing-history lookup needs SAME independently pinned full challenge + presaved secret. Current map/endpoints still independently enforce current approval/expiry/revocation and explicit registrar credential scope; legacy token APIs still refuse registrar identities. Actual Delete retains both receipt/consumed-proof history and key tombstone while removing current node.

## Publication and revocation limits, not hidden by the final guard

The guard does NOT make external config files, Multies DB and Store rename one atomic transaction. If config is removed during/after rename, same owner freezes/no success, but owning reopen can find a whole already-published UNEXPIRED initial lease. Config removal is not an implemented immediate revoke of that historical lease. Explicit Store Expire/Delete and its deadline remain current enforcement. The tested bounded in-flight/config race must not be presented as strict revocation. Before activation, product/operator expectations and actual direct-peer/relay enforcement must be settled.

The temporal late-rename case is tighter: initial access ends no later than proof/observation freshness. A rename paused past those bounds can persist consumption history, but on owning reopen that access is expired. Clock-uncertainty guard margins are admission margins, not a claim the operating system clock cannot regress or that peer traffic stops at a real-time SLA. Local policy/source changes after an already-issued lease have the bounded residual behavior above.

Ephemeral challenge/attempt/proof budgets are per retained Store process owner, NOT durable cross-restart rate limits. No automatic startup reconciliation or fresh challenge is performed. Explicit future recovery may retry SAME source reserve after owning reopen only if no consumed receipt/claim exists and current source authorizes it, using the source's original deadline. It must not reset consent/ticket/reserve/key. Permanent record/claim/index/serialized-state limits survive restart; no retention/GC/re-enrollment policy is invented. Current and historical read validation still costs O(history) under Store mutex. That remains an ingress blocker, not solved by finite development fixture counts.
